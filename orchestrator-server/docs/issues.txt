2. SecurityPolicy - ReDoS Vulnerability in Regex Patterns (HIGH)
File: orchestrator/src/main/java/com/example/orchestrator/security/SecurityPolicy.java
Issues Found:
1. Possessive Quantifiers Used Inconsistently: Some patterns use possessive quantifiers (++, *+) but others don't
2. Catastrophic Backtracking Potential: Patterns like (?i)Statement\\s++.*+execute.*+[+\\s].*+ can cause catastrophic backtracking
3. No Timeout on Pattern Matching: Despite MAX_REGEX_TIME_MS = 200, the timeout is only checked AFTER matching, not during
Example Vulnerable Pattern:
Pattern.compile("(?i)Statement\\s++.*+execute.*+[+\\s].*+") // Catastrophic backtracking on long input
Fix:
- Use atomic groups (?>...) instead of possessive quantifiers where possible
- Add timeout at the regex engine level (not just post-match)
- Consider using RE2/Joni regex engine which has guaranteed linear time

DEBUG REPORT - Systematic Investigation of Orchestrator Project
DEBUG REPORT
═══════════════════════════════════════════════════════════════
Symptom:
1. CLI commands fail with "Connection refused: getsockopt: localhost/127.0.0.1:8080"
2. Server cannot start - orchestrator module builds as CLI but has REST controllers
3. Container logs always empty - cannot debug failed builds
4. Raw socket errors shown to users instead of friendly messages
5. ReDoS vulnerability in security validation regex patterns
6. Docker daemon check uses insecure port 2375
7. No Docker image validation in sandbox
8. No SSL/TLS support in HTTP client
9. PlanReviewer creates new Scanner per loop iteration
10. ProgressRenderer creates new Spinner every 200ms
11. JSON parsing without size limits (OOM risk)
12. Race condition in Maven cache volume creation

Root cause:
1. ARCHITECTURE MISMATCH: orchestrator/pom.xml:167 configures OrchestratorCli as main class.
OrchestratorCli.execute():40 explicitly sets WebApplicationType.NONE, disabling web server.
REST controllers (TaskController, ProjectController, etc.) exist but web server never starts.
OrchestratorApplication class exists but is never used as entry point.

2. NO OFFLINE MODE: All commands (GenerateCommand, VerifyCommand, ProjectCommand, TaskCommand)
unconditionally call OrchestratorClient which makes HTTP requests. No local execution path,
no --dry-run that actually works offline, no fallback.

3. INCOMPLETE IMPLEMENTATION: SandboxService.getContainerLogs():458-468 returns empty arrays
with comment "callback API is complex". Docker-java 3.3.0 LogContainerCmd requires
LogContainerResultCallback implementation which was never done.

4. ERROR HANDLING GAP: OrchestratorClient.mapError():183-199 only handles
WebClientResponseException (HTTP responses). Connection errors (ConnectException,
ConnectTimeoutException, reactor.netty exceptions) pass through as raw throwables
with raw socket error messages.

5. REDOS IN SECURITYPOLICY: SecurityPolicy.validate():153-179 has three flaws:
a) Possessive quantifiers (++,*+) don't work as intended in Java regex engine
b) Timeout check AFTER pattern.matcher().find() - if match hangs, timeout never checked
c) Patterns like (?i)Statement\\s++.*+execute.*+[+\\s].*+ catastrophically backtrack

6. INSECURE DOCKER CHECK: DoctorCommand.checkDocker():127 connects to port 2375
(unencrypted HTTP Docker API). Modern Docker uses TLS on 2376 or unix socket.

7. NO IMAGE VALIDATION: SandboxService.createContainer():404 uses config.getDockerImage()
directly without allowlist. Configurable via application.yml with no validation.

8. NO SSL/TLS: OrchestratorClient constructor:35-39 uses basic WebClient.builder()
without .clientConnector() for SSL context, no certificate validation config.

9. BUG IN PLANREVIEWER: PlanReviewer.review():52,61 creates new Scanner(System.in)
inside while loop instead of using instance field scanner:16.

10. BUG IN PROGRESSRENDERER: ProgressRenderer.renderLoop():99-100 creates new Spinner
every 200ms (spinner = new Spinner(displayMsg); spinner.start()) instead of updating.

11. OOM RISK: GenerateCommand.parseClarificationQuestions():189 and
PlanReviewer.displayPlan():85 use ObjectMapper.readValue() on unbounded input.

12. RACE CONDITION: SandboxService.ensureMavenCacheVolume():499-505 TOCTOU between
listVolumes check and createVolume.

Fix:
1. Split orchestrator module: separate CLI main class from REST server main class.
Add spring.profiles.active=server profile for server mode, or create separate module.
Remove WebApplicationType.NONE when running server.

2. Add offline mode: Check server connectivity first, if unavailable and --dry-run/
--offline flag set, run local validation/generation without server calls.

3. Implement LogContainerResultCallback in SandboxService.getContainerLogs()
using docker-java's LogContainerCmd.exec(LogContainerResultCallback).

4. Add connection error handling in OrchestratorClient.mapError():
catch ConnectException, ConnectTimeoutException, IOException and map to friendly messages.

5. Fix ReDoS: Replace possessive quantifiers with atomic groups (?>...), add
Thread-based timeout or use RE2J engine, move timeout check inside match loop.

6. Fix Docker check: Use DockerClient.pingCmd() instead of raw socket to 2375.
Or check unix:///var/run/docker.sock / npipe:////./pipe/docker_engine on Windows.

7. Add docker image allowlist in SandboxConfig + validation in SandboxService.init().

8. Add SSL context to OrchestratorClient: WebClient.builder().clientConnector(
new ReactorClientHttpConnector(httpClient.secure(spec -> spec.sslContext(sslContext))))

9. Fix PlanReviewer: Use instance field scanner instead of new Scanner(System.in).

10. Fix ProgressRenderer: Create Spinner once before loop, update message in loop.

11. Add size limits: ObjectMapperFactory with max input size, or check string length
before parsing (e.g., if (planJson.length() > 1_000_000) throw...).

12. Fix race: Use dockerClient.createVolumeCmd().withName(volumeName).exec()
which is idempotent (returns existing if exists), remove check-then-create.
